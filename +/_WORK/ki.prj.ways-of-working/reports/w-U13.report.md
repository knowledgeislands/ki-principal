## Queries

### ORCA-PREFS-READ - How should the checker read Orca's settings until Orca offers a supported way?

**Context:** Orca 1.4.244 and 1.4.245 have no settings export or settings command. They keep settings in a live SQLite database that also holds cookies, account details and pairing records. You ruled out writing to it. Reading it in SQLite's "immutable" mode can never write or lock and never touches the sidecar files. Selecting only the declared settings keeps the secret fields unread. The catch is that it ignores Orca's write-ahead log, so while Orca runs it can show settings hours old: on sol the gap was about 11 hours. A plain read-only open would be fresh, but SQLite may open Orca's live sidecar file for writing. Copying the files elsewhere would be fresh, but it would copy the secret fields too. ki.prj.orca-evaluation has asked Orca for a supported read interface.

**Query:** Until Orca ships a supported read interface, should the checker read the live database in immutable mode, with a stated "as of" time, or wait?

**Options:**

a) (recommended, confidence medium - it is safe by construction and gives a usable check now, but it can be hours stale and it depends on Orca's private format) Read in immutable mode, selecting only declared paths. State the "as of" time and warn when Orca is running, then switch to Orca's supported interface when it lands.

b) Build the declaration now but leave the checker until Orca offers a supported read or export interface.

c) Use SQLite's read-only sidecar mode for fresher values, accepting reliance on SQLite internals and occasional refusals while Orca is writing.
