# Observatory

## Outcome

The Observatory is the operations centre for one or more territories. `apps-observatory.local` keeps the product: its Instruments observe, its Beacon ranks attention, and only a confirmed Bridge operation with a receipt may act, as its PDR-KI-OBSERVA-001 sets. The test: on any Rig, at one uniform address, Kris can read a territory's knowledge, see its threads and agent sessions, find what awaits review across its repositories, and send feedback that lands in the capture cycle, without the Observatory ever becoming an agentic editor.

Kris set this Project on 2026-10-18 (OBS-OWNER): "Fold Command centre into one Observatory Project under the Knowledge Islands model, with the Outcome "the operations centre for one or more territories" and the seven goals from the observatory-goals report; the Observatory thread is its one thread, the command-centre checkpoint closes into it, and cross-territory vocabulary stays with ways of working." It replaces the Command centre Project, whose Notes it carries below.

This Project sits in [[Themes/model|Model]].

## Goals

From Kris's words of 17 October 2026 (OBSERVATORY-CENTRE, OBSERVATORY-ATC and KB-READER), as the [observatory-goals report](<../../+/_THREADS/state-of-play/observatory-goals.report.md>) gathered them:

1. **An operations centre for one or more territories.** "this is becoming this operational centre for one or more territories ... I need to get that up and running pretty quickly."
2. **Deployed per Rig, at a uniform address, a browser tab for now.** "something which is deployed on a given rig. It's got a uniform address that it's available at ... for now ... I'm happy for it to be a tab in a browser"; a richer app only "in the future if we need to be able to access things on a machine that we can't do through that".
3. **Knowability.** "lots of knowledge capture, but knowability ... I need a way to actually see and understand that knowledge." KB-READER adds the reader stance: "look at and understand all these in a reader-only fashion", with a private side the website does not publish.
4. **Feedback that returns into the capture cycle.** "be able to feedback directly in it, which can go back into a capture cycle ... I want to acquire feedback or more knowledge in that area that I want to speak about."
5. **Documents to review, found across the territory's repositories.** "anytime there's some document to review ... It'd be nice if that document to review was able to be found ... It might not even be in the knowledge base, it might be in the specific repo which is associated to that territory."
6. **Git tooling.** "I've also mentioned about some of the git tooling."
7. **Air-traffic control over threads and agent sessions.** "see which threads are running, which sessions, agentic sessions, are associated to those ... so I can see when agents are waiting, whether they've got sub-agents that they've subbed out to ... a little bit like air traffic control."

**Non-goals.** "It's not meant to be an agentic editor; it's meant to be something which doesn't need anything to do with agents really, it's interacting with the knowledge that it can find", and "I don't want to see the updates from those sessions. I want those to still stay ... in ... my main Agentic environment". So: no prompt box, no launching, stopping or steering of sessions, and no session transcripts; Zed keeps those.

## Planned work

Kris set the order on 2026-10-18 (OBS-SLICE): "Build the four units in order: Sessions and threads Instrument, Review queue, Capture feedback as chained records in apps-observatory.local, then the tailnet name with Host network when its thread opens." Each unit becomes an ordinary record in its owning repository; Git tooling needs no unit of its own, because the Repositories Instrument exists and the 16 October intake and REPO-GIT-HYGIENE feed it.

1. **Sessions and threads Instrument** (`apps-observatory.local`). For the selected territory: Initiatives and Projects from `Streams/`, threads from `+/_CHECKPOINTS/`, and `ki agent` runs from the state folder, each linked to its Project, with a Beacon signal when an agent's status is stale or waiting. Read-only, this machine, no transcripts.
2. **Review queue** (`apps-observatory.local`, chained after unit 1). One Beacon source listing what awaits a human across every repository in scope: records awaiting review, thread reports with open queries, acquire captures at Stage and `+/` intake folders.
3. **Capture feedback** (`apps-observatory.local`, chained after unit 2). The first confirmed Bridge write: a short Markdown note with provenance written into the territory's capture landing, which [[knowledge-acquisition|Knowledge acquisition]] decides, with a receipt; every other write still refused.
4. **A name instead of a port** ([[host-network|Host network]], in `tools-rig` and chezmoi). `observatory.<name>` on each host over the tailnet, connection-critical with a tested restore path, as LOCAL-DNS asks, when the Host network thread opens.
