Grounded in [ADR-KI-HARNESS-SKILLS-017](/Users/krisbrown/workspaces/knowledge-islands/ki-agentic-harness/docs/decisions/ADR-KI-HARNESS-SKILLS-017-commit-gate-existence-and-content-are-owned-separately.md), Husky 9.1.7 as installed in tools-ki, the hooks of ki-principal and tools-ki, and a scratch-repository test of clone and worktree behaviour.

## Answers

**Do we need to use Husky?** No. Git can run hooks from any directory you point it at with one setting, `core.hooksPath`, and needs no package for that. The estate already proves it: ki-principal's committed `.githooks/pre-commit` runs `.husky/pre-commit` with plain `sh`, so Husky's own runtime never runs there. Husky is a convenience for JavaScript projects, not a requirement.

**What advantage does it bring?** One real one: when anyone runs `bun install`, Husky's `prepare` step sets the hook binding for them, so a contributor who never heard of the hooks still gets them. Smaller conveniences are that it puts `node_modules/.bin` on `PATH`, lets you skip hooks with `HUSKY=0`, and is a convention JavaScript developers recognise. Its costs are that it works only where a `package.json` exists (21 KI repositories have none), its runtime is an untracked directory that only exists after an install, so a fresh clone or linked worktree without an install commits unchecked, and it is one more dependency. The auto-binding can be had without Husky: a `prepare` script of `git config core.hooksPath .githooks` does the same thing in one line, and ki-principal's `prepare` already runs exactly that after `husky`, overriding Husky's own binding.

**Can we just put the hooks inside the `.git` folder?** We can, and Git runs them there by default, but it is the weakest place. `.git/hooks/` is never tracked, so the hooks are not reviewed, versioned or shared; `git clone` does not copy them, so every clone on both machines must be installed and kept in step by a tool, and a hook edited in one clone silently drifts. Linked worktrees do share the clone's `.git/hooks/`, so worktrees are not the problem; clones are.

**Or is it better outside the `.git` folder?** Yes. A tracked directory such as `.githooks/` puts the hook in the repository, so it is reviewed and versioned with the code, every clone and every worktree gets the same hook at the revision it has checked out, and a change reaches the other machine with an ordinary pull. The only per-clone step left is the one-line binding, `core.hooksPath .githooks`, which `prepare` sets in a Bun repository and `ki repo conform` or the estate sweep sets everywhere else. This is what [ADR-KI-HARNESS-SKILLS-017](/Users/krisbrown/workspaces/knowledge-islands/ki-agentic-harness/docs/decisions/ADR-KI-HARNESS-SKILLS-017-commit-gate-existence-and-content-are-owned-separately.md) already requires.

## Recommendation

**b) Hooks tracked in `.githooks/`, without Husky** (confidence medium - once a committed stub is bound, Husky does nothing a one-line `prepare` does not, and dropping it gives every repository one hook home and makes KB-AUDIT moot; medium because it changes `SCR-11` and `PKG-5` in `ki-engineering` and touches all 25 Husky repositories' manifests, where a) keeps Husky and changes less).

The choice between a) and b) does not change the rollout's shape: both bind `.githooks` in every clone, both need the tools-ki composition, binding and sweep in [hooks-standard.md](hooks-standard.md) section 4, and the Bun wave edits `prepare` in each repository either way. b) also removes the stub's hand-over line and the effective-gate reading that `GATE-1`, `GIT-2` and `SHELL-HOOK` would otherwise need, because content is always in the stub they already read. c) and d) are not recommended: c) leaves package-less repositories and uninstalled worktrees ungated, and d) moves the hooks out of review and makes every clone an installation to keep in step.
