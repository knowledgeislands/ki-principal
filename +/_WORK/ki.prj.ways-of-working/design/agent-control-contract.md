## Scope and ownership

[tools-ki](../../../../../tools-ki/README.md) owns command parsing, runtime adapters, process control, queue transactions, receipts and tests. The [KI Agentic Harness](../../../../../ki-agentic-harness/README.md) owns the portable behaviour in `ki-delegation`, the wake and steering rules in `ki-coordination`, authority-footer wording and generated prompt/report surfaces. This island holds this proposal and Kris's acceptance. No new roadmap record, scheduling service, hosted notifier or estate rollout is part of this build.

The proposed build order separates the control core from native wake:

1. Accept the revised contract's policy independently of the candidate model pins. A first tools-ki run implements and verifies attempt identity, containment refusal, stop, dequeue, spawn reconciliation and launch defaults in isolation. It does not implement or enable wake. Role profiles remain dormant until their evidence gates pass.
2. A separate Harness run aligns its authority tiers, none footer, scoped acceptance supplement, skills and generated surfaces with the verified first interface. No `--role accept` launch or dispatch is permitted until this Harness acceptance wording and the CLI declaration validator are both verified together; the first build must refuse that capability until then. No role launch precedes its model evidence gate.
3. After independent review of the first build and Harness alignment, commission wake as its own later tools-ki build, including delivery reconciliation. Require per-runtime native capability evidence before enabling that adapter; an unsupported adapter remains a query. A separate Harness alignment and combined review follow the verified wake interface before any separately authorised activation.

Each tools-ki run reports its Harness handoff for the coordinator to send as one message to the receiving work. It has no authority to edit the Harness. Handoffs create no roadmap record. Release, installation and live activation remain separately authorised work; contract acceptance alone enables none of them.

## Shared identity, states and receipts

A command resolves the run's recorded work home, independently of the target working directory. It refuses an ambiguous home, a foreign machine's runtime packet or a mismatched work identity. It never searches process names, guesses a repository from a basename or treats a PID alone as ownership evidence.

A launched attempt has an immutable identity: run, agent, attempt number, random launch token, runtime, physical working directory, process birth identity, session/process-group identity and the launcher that owns it. A queue entry has its own immutable entry ID, reserved attempt and launch token before dispatch. Receipts name these identities and UTC timestamps, with readable local times in text output. Existing attempts without adequate ownership evidence remain observable but cannot be signalled automatically; they need a new explicitly authorised launch, not retroactive trust in their PID.

Every new control supports `--json`. A versioned receipt (`ki/agent-control/v1`) includes operation ID, operation, run, target identity, previous state, resulting state, outcome, reason, timestamp and associated event sequence where applicable. The durable machine-local journal is written before an external effect; a later receipt records the observed outcome. Retries reuse an operation ID through `--request <id>` and return the recorded outcome, unless the same ID is presented with different arguments, which is refused. Exit 0 means a confirmed result, including an explicit idempotent no-op; exit 1 means refusal, conflict or unconfirmed outcome; exit 2 means invalid usage. An acknowledged request alone is never a successful stop or wake.

Queue state is `queued -> claimed -> started`, or `queued/claimed -> cancelled` before spawn. Attempt execution is `held/running -> stop-requested -> stopped`, or `stop-requested -> stop-timeout` while still live. Natural `done` and `failed` remain distinct. These are runtime states, not new states for the work package. No control changes a roadmap record or writes a work-package state, acceptance, report or `DONE` on the worker's behalf.

Extend the append-only run-event vocabulary with `stop-requested`, `stopped` and `dequeued`. A timeout or lost ownership produces a `blocked` event with the operation ID. `wait --next` returns each unseen `stopped` or `dequeued` event as well as today's terminal/query events; `watch` and status render them. A stopped or dequeued predecessor closes its dependants' gates as blocked; it never satisfies a `DONE` gate. `ALL FINISHED` requires an empty queue and no held, running, claimed or unconfirmed live attempt. An armed watcher alone does not keep a run busy. Receipt retries and event derivation cannot emit duplicate terminal events.

## Stop

Proposed surface: `ki agent stop <run> <name> --attempt <n> --reason <text> [--grace <seconds>] [--request <id>] [--json]`. The attempt is required so a delayed instruction cannot stop a later relaunch. Grace defaults to 30 seconds and accepts 1-120 seconds. The command applies to one launched or held attempt. A queued entry is refused with its dequeue command; it is not silently removed.

Stop is signal-driven graceful termination, not a promise that the worker has completed a cooperative checkpoint. Under the per-run control transaction, record the stop request and fence that attempt against a gate opening or a delayed spawn. Verify the launch token, process birth identity and exclusive ownership immediately before sending SIGTERM to the attempt's contained process groups. The containment scope must exclude the coordinator, dispatcher, watcher and other attempts. A single process group is insufficient: a descendant may double-fork, call `setsid` or change groups while still writing to the working directory. The runtime adapter must prove that its host facility prevents escape or continuously accounts for and controls every descendant, including after reparenting and group/session changes, without PID-only trust or a race between enumeration and signalling. If it can prove only group membership, return `containment-unverified`, exit 1, send no signal and leave the adapter unsupported for confirmed stop. Do not relabel a group-only signal as an attempt stop.

A held gate process and any runtime it could start share the stop fence and containment record. Their transition to runtime launch is serialised with stop. Stop cannot acknowledge success while a gate process can still launch the worker. Observe the whole containment scope until it is empty or grace expires, rechecking ownership and descendant coverage throughout. Record `stopped` only after the scope is empty and cannot spawn again, not merely after the original group disappears. If the attempt completed naturally first, return `already-terminal`, exit 0, with that natural outcome as a confirmed no-op, not a successful stop. A dead process without a prior stop or successful report remains `failed`, not successful completion. A repeated confirmed stop returns `already-stopped`, exit 0.

At grace expiry return `stop-timeout`, exit 1, leave the attempt visibly live and emit `blocked`. No automatic SIGKILL or escalation option is included in this first build. A changed or unavailable ownership identity gives `ownership-unverified`, sends no signal and requires the coordinator's attention. If SIGTERM was sent but observation becomes uncertain, retain an unconfirmed stop and never describe it as stopped.

The coordinator uses stop only on an explicit owner instruction naming the work, or a stop condition explicitly preauthorised in that attempt's brief. A new owner message is steering, not such an instruction. Stop never discards edits, rolls back a transaction, deletes a worktree or lock, commits files, accepts work or marks the run done. The worker may leave a partial effect; the receipt points the coordinator to the preserved log, status and working directory for review.

Today's gap: `AgentProcesses` exposes launch, liveness and sleep only; attempts record a PID and launch options, not a verifiable process-ownership contract. There is no stop command, stop fence or stopped event. Build the process-port operations and attempt identity first, including safe refusal for old packets.

## Dequeue

Proposed surface: `ki agent dequeue <run> <name> --entry <id> --reason <text> [--request <id>] [--json]`. Queue and status expose the entry ID. Dequeue means prevent this queue entry from starting; it does not mean stop a worker or pause the dispatcher.

Queue append, dispatcher claim, dequeue, held-to-runtime transition and final spawn authorisation use one per-run transaction protocol with atomic persistence and a recoverable claim journal. A dispatcher records a claim before taking an entry out of the pending view. It must revalidate that claim and its cancellation fence inside the spawn-authorisation transaction. Holding the transaction through spawn and recording the returned process identity makes the winner observable; a crash in that interval leaves an unconfirmed claim that blocks replacement launches until reconciled. Never infer that an entry disappeared because it launched successfully.

If cancellation wins while queued or claimed but not spawned, write a persistent tombstone and a `dequeued` event; return `cancelled-before-start`, exit 0. Preserve the brief and launch options as evidence. If spawn won, return `already-started`, exit 1, with its attempt identity and the exact stop command. If a prior cancellation won, return `already-dequeued`, exit 0. A completed attempt returns `already-terminal`, exit 0, as a confirmed no-op without pretending it was dequeued; an unknown entry is refused, exit 1. An unresolved spawn returns `claim-unconfirmed`, exit 1, with `ki agent recover inspect <run> --operation <id>`, never a cancellation success. A relaunch or deliberate requeue uses a fresh entry and attempt identity and cannot inherit or erase an earlier cancellation.

After restart the dispatcher honours tombstones and reconciles unconfirmed claims before taking more work. It cannot clear a cancellation by rewriting an older queue snapshot. Dequeue never signals a process, deletes a prompt or packet, reprioritises other entries, cancels dependants silently or broadens the concurrency limit.

Today's gap: dispatch reads `queue.jsonl`, removes a selected entry and then calls launch. There is no claim acknowledgement, cancellation tombstone or transaction joining dequeue to dispatch. Reusing only the events-file lock is insufficient unless all these queue and launch transitions participate in the same protocol.

## Reconciliation after uncertain effects

Recovery has its own `ki agent recover` namespace. The existing decisions-log command `ki agent reconcile <run> <entry> [home]`, including its `--class` option, remains unchanged in name, grammar, help, exit behaviour and effects. It is neither re-homed nor aliased; `inspect` and `resolve` remain valid run names for that command.

Proposed surfaces: `ki agent recover inspect <run> --operation <id> [--json]` and `ki agent recover resolve <run> --operation <id> --evidence <local-json-path> --authority <local-path#heading> [--request <id>] [--json]`. Inspect is read-only and returns the frozen operation, uncertainty, reserved identities, journal position and exact evidence required. Resolve is an explicit coordinator action under a cited recovery decision, serialised with dispatch, stop and continuation leases. It records the decision reference/digest, evidence file/digest, prior uncertainty, verified observations, resulting state and original operation ID in a durable reconciliation receipt. Missing, contradictory, stale or unverifiable evidence returns `reconciliation-unconfirmed`, exit 1, and leaves all fences and pending events intact. A confirmed resolution is exit 0; repeated identical resolutions are idempotent. Resolution never itself spawns, signals, resumes, accepts or deletes anything.

The evidence document has schema `ki/agent-reconciliation/v1`, with `operation_id`, `target_id` (the reserved attempt or delivery key), `observation` and `proofs` (non-empty local adapter evidence references and SHA-256 digests). The permitted observations are `spawn-started`, `spawn-not-started`, `wake-delivered` and `wake-not-invoked`; the CLI validates the matching operation kind and adapter proof rather than trusting the operator's assertion. Proofs must cover the frozen operation and its current containment or native session identity. The owner decision authorises recovery, not an override of missing safety evidence.

For spawn, reserve the launch token and adapter-managed containment identity durably before creating a child. Pass the token to a launcher-owned supervisor, whose first action durably acknowledges its birth identity and scope before any worker or runtime can start. A separate persisted spawn authorisation opens that supervisor's gate. The adapter must support lookup of this pre-reserved token in its own managed scope after a crash, even if the parent never received a PID; this is not a process-name search. Before authorising a worker, the supervisor participates in the same cancellation transaction. Supervisor registration alone does not prove a worker started: require its verified worker-start record or a currently verified owned worker identity to establish `spawn-started`, bind that identity and return the stop command without duplicate launch. A consumed authorisation without proof of the worker outcome stays unconfirmed. `spawn-not-started` requires proof that no worker authorisation was consumed and that every possible supervisor/descendant is absent or durably fenced from opening its gate; a missing acknowledgement or PID alone proves neither. Reconcile to the preserved cancellation tombstone if present, otherwise return the entry to `queued` with its original frozen selection. An adapter unable to prove either case keeps the claim blocked for owner-assisted local inspection; starting a replacement is forbidden while that uncertainty remains.

For wake, inspect the native adapter's delivery-key acknowledgement or native session delivery record. `wake-delivered` requires proof tying the exact session, binding and event range to accepted delivery, then advances the delivered cursor once. `wake-not-invoked` requires positive adapter/journal proof that invocation never crossed the native boundary; it returns the batch to pending, with all ordinary expiry and authority guards still required before retry. Absence from a transcript, a quiet session or a missing acknowledgement is insufficient. An invoked but unacknowledged delivery remains suspended unless native evidence proves delivery; do not assume it was lost. If the adapter cannot settle it, the coordinator brings the operation ID and evidence to the owner and leaves wake suspended. They may continue manually only after verifying exclusive native session ownership, under the existing bounded authority; the CLI must not clear the uncertainty or redeliver that batch merely because the owner chose manual continuation.

## Bounded wake

Proposed surfaces:

- `ki agent wake arm <run> --runtime <claude|codex> --session <native-id> --until <UTC-time> --authority <local-path#heading> [--request <id>] [--json]`.
- `ki agent wake status <run> [--json]`.
- `ki agent wake disarm <run> --binding <id> --reason <text> [--request <id>] [--json]`.

Arming requires an explicit owner-authorised autonomy window recorded at the supplied decision reference. That heading must contain exactly one JSON fenced block with `schema: "ki/autonomy-window/v1"` and fields `window_id`, `work`, `not_before` and `expires_at`; the last two are RFC 3339 UTC timestamps. These are JSON object keys and string values, not YAML syntax. The block is the recorded read-back of the owner's bounded grant, confirmed by the owner or under their explicit delegation, not a window invented by the CLI. The tool parses it, checks the work identity and current time against its bounds, and requires `now < --until <= expires_at`. An omitted expiry, missing or malformed block, ambiguous heading or mismatched decision is a refusal before watcher creation. It records the decision and block digests; the coordinator remains responsible for the grant's meaning. No command invents, extends or renews authority. Disarm is local and idempotent and never stops workers or the coordinator.

The immutable binding contains the work ID and physical work home, exact native runtime/session ID, owner-decision reference and digest, expiry, registration event cursor and one continuation lease. The adapter verifies that the native session belongs to that work and can be resumed locally without opening a new conversation. Reject a missing, ambiguous, busy or unsupported session; never choose the most recent session, an unrelated terminal or a GUI tab. A change in work-home identity or decision digest suspends the binding. A session being quiet is not evidence that it is idle: interactive turns and resumed turns must participate in the same exclusive continuation lease. An adapter unable to prove that exclusion refuses arming.

Arming starts one detached watcher, with a receipt including binding and watcher identities. It survives the launching terminal and watches events without consuming `wait --next`'s cursor. The default cursor is the current tail: old events do not cause surprise continuations. Within the window, a new `done`, `failed`, `blocked`, `needs-owner`, `stopped` or `dequeued` event is eligible; plain status lines, milestones and five-minute heartbeat ticks are not. Coalesce eligible unseen events into one pending continuation, with their sequence range. Wake uses the current work send line as its message and adds only the event identities and the instruction to re-read the package, not a new brief or a new authority grant.

Binding states are `armed`, `pending`, `resuming`, then `armed` after acknowledged delivery; `expired`, `disarmed`, `suspended` or `error` end automatic delivery. Check expiry, grant digest, work state and session lease immediately before every resume. On hold, Finished or a handoff to the supervisor suspends automatic continuation, leaving the events visible. A busy session keeps one pending batch until idle or expiry, with no parallel resume. Expiry ends the watcher and pending automatic delivery, leaving workers and unread coordinator events intact.

Use a persistent delivery key comprising binding ID and event sequence range. Record the pending delivery before invoking the adapter. The adapter must return a native acknowledgement tying the same session to that key; acknowledgement means the native session accepted that keyed continuation, not that the watcher wrote to a pipe or that the coordinator finished the work. Commit the delivered cursor only on that acknowledgement. A crash after invocation but before acknowledgement gives `delivery-unconfirmed`: do not retry blindly or claim exactly-once native delivery. Suspend delivery and expose `ki agent recover inspect` and `ki agent recover resolve` from the reconciliation section; restart may retry only a delivery proven not invoked. Confirmed delivery, repeated arming requests and watcher restarts must not resume the same batch twice. A second binding is refused while one is armed or a continuation remains in flight, including unconfirmed delivery after expiry or disarm. Disarm or expiry cannot interrupt an already acknowledged continuation; the resumed coordinator must itself obey the grant's expiry before launching more work.

Wake never creates a new session as a fallback, sends email or chat, changes a scheduler, resumes without a matching grant, launches workers directly or accepts work. It never changes work-package state itself. Native continuation is a required local adapter capability; if either runtime cannot establish ownership, busy-state exclusion and acknowledgement, that adapter remains explicitly unsupported and its wake build is returned as a query rather than simulated with a fresh `exec` call.

Today's gap: `wait --next` prints an event and advances its read cursor; `watch` prints events/status and exits at completion. Neither binds or resumes a coordinator session, records an autonomy window or implements a continuation lease and delivery journal. The Harness describes OOS-WAKE as agreed but explicitly leaves out-of-session runs waiting for the owner's send line until tooling ships.

## Launch defaults

Add `--role <mechanical|plan|build|review|accept|prune|release>` and `--authority <local-path#heading>` to role-based launch and queue requests. Role-free launch and queue requests retain their existing authority and `--rules` behaviour; the new `--authority` requirement applies to role launches only. Add `--dry-run --json` to resolve and display the effective request, sources of each value, required authority and any refusal before writing a packet, creating a worktree or spawning. A queued request freezes that resolved result and its profile revision; dispatch validates it again but never silently re-resolves it against changed defaults.

### Precedence and safety

Resolve each field in this order: explicit option, accepted role profile, legacy default only when no role was supplied. Do not infer a role from an agent's name, prompt text, folder or file suffix. Unknown roles fail. A role-free invocation retains today's Claude runtime, omitted model/effort and `none` footer for compatibility, and its receipt labels that path `legacy`. Role-based launches must pin model and effort.

Explicit options win only within the role's constraints. Changing runtime requires an explicit model valid for that runtime; it cannot inherit a model from the other runtime's profile. Review and accept refuse a runtime/model other than their accepted Codex pin unless an explicit cited owner decision authorises that exact alternative with local evidence. There is no inferred provider-wide model ranking. An acceptance run requires the `none` footer plus the scoped declaration below and refuses a prune or release footer; prune and release roles require their matching footer. An explicit footer above `none` for any other role requires cited owner authority and cannot make a review into an implementation run. Invalid combinations fail before any launch side effect. Explicit extra directories, gates, worktree and repository options retain their existing meanings and do not acquire wider defaults.

A role supplies no owner authority. For role launches, `push`, `prune` and `release` require an explicit existing `--authority` reference to the bounded decision, recorded in the launch receipt and brief. `accept` additionally requires `--acceptance <local-json-path>` on launch or queue. The JSON object has schema `ki/agent-acceptance/v1`, with these required fields:

- `authority`: the exact existing local path and heading supplied by `--authority`, and `authority_sha256`: the SHA-256 digest of that cited heading's content.
- `override`: the literal `accept-named-records-only`, declaring the owner's task-specific exception to the footer's acceptance ban, with no pruning, deletion, release or remote authority.
- `records`: a non-empty array of objects, each with the full `id`, absolute local `path`, `sha256` of the record being reviewed, and a non-empty `reviews` array. Each review identifies its absolute report `path`, `sha256`, `reviewer_attempt` and `delivery_attempt`; reviewer and delivery must be distinct recorded identities. Paths must resolve to the declared records and reports. Wildcards, duplicate IDs, missing evidence and mismatched identities or digests are refusals.

The caller records the owner's grant and the independent review prerequisite in this declaration and the brief. The CLI validates its closed shape, references, digests, record identities and recorded reviewer/delivery separation before any launch effect; it cannot judge the owner's prose or the quality of the review. `--role accept` without the declaration, with `--rules prune`, with a missing authority reference or with evidence that fails validation is refused. Dry-run displays the full effective declaration and refusal. Queue freezes the declaration and its digest; dispatch revalidates the authority, record and review digests and never silently updates them. A changed record needs a fresh declaration and review evidence. Receipt and `.launch.json` contain the authority reference/digest, exact named record IDs/paths, declaration/digest, review identities and acceptance wording capability revision; the rendered brief carries the same bounded exception.

Before any accept-role launch or dispatch, the Harness must have revised its tier table, none footer and generated surfaces to recognise this explicit scoped acceptance exception, and the CLI must validate that supported wording capability. Existing push-only precedence does not suffice. If the installed Harness still says that no task-specific declaration may override the acceptance ban, return `acceptance-contract-unavailable`, exit 1, without launching. The blanket ban remains in force outside the exact declared records. An acceptance grant neither requires nor implies pruning or remote access. Push is available only through a separately explicit grant covered by cited owner authority, and never follows `accept`; `--allow fetch` and `--allow machine` also remain explicit.

Prune remains its own role and separately authorised lifecycle action, after acceptance and its required terminal-state commit. An acceptance run cannot acquire prune's push or deletion capabilities by selecting its role or declaration. A footer is a constraint and an authority description, not proof that any named record was accepted.

Extend `.launch.json` with schema version, role, effective runtime/model/effort/footer/grants, per-field source, profile revision, authority reference/digest, entry/attempt identity and work home. Preserve the effective values through queueing, gates and relaunch; a deliberate new request may choose new values, but never rewrites an older attempt's receipt. Print the effective selection in launch and queue receipts so the coordinator can see a wrong model before it runs.

Today's gap: launch and queue default to Claude and `--rules none`, omit model and effort unless supplied and have no role option. Runtime adapters pass explicit model/effort through. `.launch.json` records runtime, optional model/effort and workdir/worktree, not role, footer, grants, provenance or authority. The prune footer explicitly says never accept work; it cannot become acceptance authority merely by being selected. This is a non-breaking choice: role-free `--rules push|prune|release` launches and queue requests keep today's behaviour, with no new `--authority` requirement. The new authority requirement applies to role launches, including queued role requests; it does not add a grant or remove the existing requirement for owner authorisation.

## Evidence gates before enablement

The build report must distinguish offline fixture results from local native evidence, linking each capability to the tested host, adapter/runtime version, immutable attempt/session identities, procedure, observations and limitations. Use prior local evidence or a separately authorised bounded evaluation; this drafting run performs neither live model evaluation nor native session continuation.

- Stop containment: demonstrate descendant coverage with a runtime child that changes session/group and reparents. Show that stop covers the whole attempt without signalling another attempt. If the host cannot prove containment, the refusal path may ship, but confirmed native stop remains unsupported.
- Native wake exclusion: for each runtime separately, demonstrate that an interactive turn and a resumed turn contend for the same native session lease, including two watchers, reconnect, crash and a busy session. A tool-local lock without interactive participation is insufficient. Without this evidence, arming that runtime is refused.
- Native acknowledgements: demonstrate a native acknowledgement and recoverable lookup for the exact session/delivery key, including acknowledgement loss and restart. A successful process exit or pipe write is insufficient. Without this evidence, the adapter cannot claim delivery or enable wake.
- Model suitability: for each proposed role pin, cite the native ID, supported effort, local availability and role-relevant evaluation reviewed by the owner or their authorised reviewer. Use bounded representative planning, implementation or independent review evidence as appropriate; historical usage establishes neither comparative strength nor suitability. Record the accepted binding and evidence revision. Without it, the role profile stays dormant; an explicit alternative also needs the cited approval and evidence.

## Acceptance tests for the build

Use injected process, clock, filesystem and continuation ports. These tests run offline with no live worker, native session, credential, signal to an unrelated process or external service. Keep command-help and JSON-schema assertions alongside behaviour tests. The build report distinguishes passed fixture tests from native adapter capabilities still unproved.

1. Identity and compatibility: legacy packets remain readable; old or forged PID-only ownership is refused without a signal. Relaunch allocates a new attempt/token. A delayed stop cannot target that attempt. Invalid arguments, foreign homes and duplicate operation IDs with changed payloads leave all state unchanged.
2. Stop: test running and held attempts, natural completion racing SIGTERM, already-stopped retries, dead-before-request failure, PID reuse, foreign process groups, permission errors and ownership loss after signalling. Exercise descendants changing groups/session, double-forking and reparenting; disappearance of the original group alone must not produce `stopped`. Test containment refusal, whole-scope disappearance and grace expiry with an injected clock. Exactly one stop receipt/event is derived, no SIGKILL is sent and no unrelated process is touched. Assert exit 0 for `already-terminal` and `already-stopped`, exit 1 for timeout or unverified containment, without treating a natural failure as a successful stop.
3. Stop against a held gate: exercise both orders of gate-open and stop, including a crash during transition. A confirmed stop leaves no possible later spawn; uncertain state blocks replacement work. A stopped predecessor blocks its dependants and never opens a `DONE` gate.
4.
