## The handoff, as received

### Handoff: per-host configuration (and, optionally, a coarse acquisition kind) for the public catalogue

Context: rig.midnight.ninja (repo `krisb/apps-rig.midnight.ninja`) publishes Rig's `public` view as a catalogue with one column per Mac: terra (`laptop` profile) and sol (`studio` profile). Its pull (`apps/site-rig/pipeline/pull.ts`) runs `rig export --profile public` (tool id, name, category, purpose, rationale, platforms, relationships) and `rig show --profile laptop|studio --format json` (`tools[].id`, intersected with the public view, written to `data/host-tools.json`). The page has a cell state ready for "this host gives the tool its own configuration" (an "own config" label under the tick), with no data behind it yet. Kit expects terra and sol to diverge mainly through configuration rather than through which tools they carry.

Ask A, per-host configuration membership (needed): for a resolved complete profile, say which selected tools that profile configures. Rig decides what "configures" means; the natural reading is that the profile selects at least one Rig-owned resource linked to the tool (a setting, Dock item, default application, service or similar). Today `[setting.*]` is keyed by preference domain and carries no `tool` link, so this probably needs an optional `tool = "ID"` link on settings, mirroring Dock items and default applications, or a mapping Rig derives itself. Contract the site would consume (any equivalent shape is fine): in `rig show --profile <P> --format json`, each `tools[]` entry gains `"configured": true` when P selects at least one resource linked to that tool, false or absent otherwise. Boundary: a boolean per tool and profile only, no setting keys, values, domains, paths, file contents or counts; `rig export --profile public` stays exactly as narrow; no live or observed state, declared intent only. Done when: `rig show` for laptop and studio carries the flag; fixture tests cover a tool configured in one profile and not the other; the user guide documents the link from a resource to its tool.

Ask B, a coarse acquisition kind in the public export (optional; only with Kit's go-ahead): one coarse enum per public tool, for example `"kind": "application" | "command-line" | "package"`, derived from the install kind; never the locator, provider name, cask or App Store ID, or version. `pull.ts` has a forbidden-field guard (`version`, `install`, `locator`, `provider`, ...), so the field must not be called `provider` or `install_kind`.

Not for Rig, for awareness: 62 Homebrew packages migrated from the Brewfile still carry the placeholder rationale "Retain the explicit package choice from the former managed Brewfile..." (a `krisb/dotfiles` data task; the site counts them as "Awaiting a rationale"). vega (`agent-host`) has no public view, so no column.

When it lands: tell the apps-rig.midnight.ninja side the final JSON shape; it will extend `pull.ts` to write `profiles.<profile>.config: [ids]` into `data/host-tools.json`, which the page already reads.
